# M1 유물 도메인 설계

## 목표

정예전을 이겼을 때 유물 3개 후보 중 하나를 고르고, 선택한 유물을 이후 전투에서
결정론적으로 발동시킨다. 저장 파일은 계속 `seed`, `characterId`, `actionLog`만
보관한다.

## 경계와 데이터 흐름

`lib/domain/model/relic.dart`는 `RelicDef`, `RelicTrigger`, sealed `RelicEffect`를
정의한다. `lib/data/m1_relics.dart`가 15개 정의와 업 축의 선택 의미를 소유한다.
`RunContent`가 유물 풀을 주입하고, `RunProgress`가 액션 로그를 재생해 보유 유물
목록을 만든다. `RunState`에는 보유 목록이나 후보를 넣지 않는다.

정예 승리 뒤에는 카드 보상 대신 `RelicReward`를 보류하고 `ChooseRelicReward`만
로그에 기록한다. 후보는 정예 노드의 전용 파생 시드와 `RngStream.reward`에서
되살린다. 카드·상점·사건의 reward salt와 다른 `relicRewardSeedForNode`를 둔다.

## 전투 발동

`beginCombat`이 보유 유물을 받고 `CombatState`가 이를 유지한다. `_Sim`만 유물
효과를 해석하며, 발동 시점은 전투 시작, 턴 시작, 카드 사용 뒤, 턴 종료, 적 사망,
플레이어가 준 무방어 피해, 플레이어 피격 전이다. 유물은 선언만 하고 피해·방어·
드로우·상태·업 규칙은 엔진의 기존 공통 경로를 재사용한다.

`previewDamage`와 `previewBlock`은 복제한 `_Sim`에서 실제 카드 해결과 같은
유물 훅을 실행해 값을 계산한다. `previewEnemyDamage`는 실제 피격 전 감쇠 훅과
같은 경로를 쓴다. 따라서 표시와 결과가 갈라지지 않는다.

## 유물과 업 축

15종은 고업 보상, 저업 보상, 업의 자원 환산, 업 정화, 처치 순서와 생존이라는
서로 다른 결정을 만든다. 정확한 수치는 `CombatTuning`에, 정예 보상 장수와 업
상승량은 런 보상 수치이므로 `RunTuning`에 둔다.

## 정예 경제

정예의 기존 노잣돈 2배는 유물이 없던 시기의 임시 보상이다. 이를 제거해 §2.1의
`유물 보상 + 업 상승`으로 바꾼다. 첫 상점 루프는 정예 수입에 의존하지 않는다:
일반 전투 보상 30과 상점 카드 가격 30이 같고, `전투 하나 뒤 상점 구매 액션` 회귀
테스트가 실제 경로를 계속 검증한다. M2 시뮬레이터 전에는 이 막힘 방지만 보장한다.

## 저장 전환

새 `chooseRelicReward` 액션은 구버전 v2가 알지 못하므로 `runSaveVersion`을 v3로
올린다. v2 파일은 기존 정책대로 거부하고 파일을 보존한다. 새 저장은 액션 id만
추가하며 보유 유물·후보·전투 RNG를 저장하지 않는다.

## 제외 범위

UI, 상점 유물 판매, 카드 강화, 보스 전용 최상급 유물 보상은 구현하지 않는다.
보스 콘텐츠가 생기면 악업 구간 최상급 후보를 `relicRewardForNode`의 별도 분기로
붙인다.
